# CLAUDE.md / AGENTS.md

Guidance for coding agents (Claude Code, Codex, Cursor, Copilot and others) working in this repository. The file lives at `.claude/CLAUDE.md`; the root `AGENTS.md` is a symlink to it.

This file holds the rules for every change. Rules for one part of the tree live in `.claude/rules/`, one file per area, listed in the index under "Area rules" below.

## Repository overview

Skyhook (being renamed to NodeWright) is a Kubernetes-aware package manager for safely modifying host infrastructure at scale. It coordinates the node lifecycle (cordon → drain → apply package → interrupt/reboot → uncordon) as controlled rollouts gated by interruption budgets and deployment policies.

Rename status: the project is moving from Skyhook to NodeWright. Already moved to `nodewright`: the install namespace (`nodewright` for new installs; existing installs stay in `skyhook` forever, since namespaces cannot be renamed in place), the Go module (`github.com/NVIDIA/nodewright/operator`), the Helm chart (`name: nodewright`, distributed at `oci://ghcr.io/nvidia/nodewright/charts/nodewright`), the operator image (`ghcr.io/nvidia/nodewright/operator`), the agent image (`ghcr.io/nvidia/nodewright/agent`, since `agent/v6.4.2`), the primary CRD group (`nodewright.nvidia.com/v1alpha1 NodeWright`; the legacy `skyhook.nvidia.com` group is kept read-only for a migration window), and the CLI plugin (`kubectl nodewright`, binary `kubectl-nodewright`). Don't "fix" `nodewright` references back to `skyhook`, and don't preemptively rename what hasn't moved yet.

## Components

- **`operator/`**: Go controller-manager (controller-runtime, Kubebuilder v4), vendored. Also hosts the `kubectl nodewright` CLI (`cmd/cli`).
- **`agent/`**: Go module, vendored. The static binary that runs inside every package container and executes the lifecycle steps.
- **`chart/`**: the Helm chart, a hand-maintained mirror of `operator/config/`.
- **`tools/`**: stdlib-only Go module for release and repository tooling.
- **`k8s-tests/`**: chainsaw e2e suites. **`docs/`**: user and contributor docs, indexed by `docs/README.md`.

The root `Makefile` fans out into `operator/`, `agent/` and `tools/`; most real targets live in `operator/Makefile`. `make help` lists the targets in each.

## Domain vocabulary

**Status**, **State** and **Stage** are three distinct concepts, named to look alike. Mixing them up causes subtle bugs. Full definitions are in `docs/architecture/operator-status.md`.

- **Status**: the health of a NodeWright or a node as a whole (`complete`, `blocked`, `waiting`, `paused`, `disabled`, `in_progress`, `erroring`, `unknown`), derived from the States of its packages.
- **State**: the outcome of one package on one node (`complete`, `in_progress`, `skipped`, `erroring`, `unknown`).
- **Stage**: the lifecycle phase a package is in (`uninstall`, `uninstall-interrupt`, `upgrade`, `apply`, `config`, `interrupt`, `post-interrupt`; all but the two interrupt stages have a `*-check` counterpart).

A field, variable or log key named for one of the three carries only that concept.

Packages run **Uninstall → Apply → Config**, or **Upgrade → Config** on a version bump. Packages with interrupts add **Interrupt → Post-Interrupt**, with the node cordoned and drained before Interrupt. Semantic versioning is strictly enforced so the operator can tell upgrade from downgrade from fresh apply. Per-node state lives in Node annotations (`nodewright.nvidia.com/nodeState_<name>`, where `<name>` is the CR's `metadata.name`), not on the CR.

Before changing an existing feature, read how it works today in `docs/architecture/` and `docs/user-guide/`, and its ADR in `docs/designs/` for why; an ADR condensed from an older design links the full original from its Status. Check `docs/plans/` before starting new work in an area. Architecture decisions are recorded as ADRs per `docs/designs/README.md`. Never rewrite an accepted ADR: say in the PR description what departs from it. If the docs are silent on a question you need answered, say so rather than guess.

## Working rules

1. **Read before writing.** Never edit a file you haven't read.
2. **Use project patterns; justify new ones in the PR description.** Find the nearest existing example in the same package and match it: error wrapping, the `dal`/`wrapper` indirection, Ginkgo spec structure, controller-runtime idioms, where constants live. If the pattern you are about to introduce doesn't exist in the target package yet, stop and ask whether it should. If you go ahead, say in the PR description what you introduced, why the existing patterns didn't fit, and why the new one should become the convention. Silent divergence is rejected in review.
3. **Don't add what wasn't asked for**: no speculative abstractions, config knobs or scope creep.
4. **Three strikes.** After three failed attempts at the same fix, stop and reassess instead of piling on code.
5. **Prefer editing to creating.** Make a new file only when the code doesn't belong in an existing one.
6. **Comments explain the unusual, briefly.** Default to none. When code does something surprising, a sentence or two says what and why. Never narrate the code, and never point at other files or functions: those references go stale unnoticed.

## Before you open a pull request

Run the make targets CI runs, on your machine, before you push. This applies to a coding agent exactly as it does to a person.

- **CI runs the Makefile, so you should too.** From `operator/`, CI's unit lane is `make vet lint unit-tests`; run all three, since `make unit-tests` alone does not lint. From `agent/`, it is `make test lint`; from `tools/`, `make test`. Unit tests and lint need nothing external. Docs-only changes need none of this. A change is not done until these pass; never skip or disable a test to make CI green.
- **Never use raw `go test` / `go build` / `golangci-lint run` instead.** The targets pass `-mod=vendor`, apply license headers, sequence CRD, deepcopy and mock generation, and install their own tools (envtest, ginkgo, golangci-lint) into `bin/`. A missing tool means the target was bypassed, not that a suite can be skipped. Drop to a raw command only for a narrow case the Makefile doesn't cover, such as running a single spec; a workflow you will repeat gets a make target instead.
- **Iterate locally, fastest loop first.** `make vet lint unit-tests` needs no cluster and runs in minutes, so iterate there. Once it is green, run the e2e suites you touched (or `make test` in `operator/`, which needs `AGENT_IMAGE`) against a local kind cluster; see `.claude/rules/tests.md` for what they need. Even that beats pushing to see what CI says: workflow runs from a fork wait for a maintainer to approve them, which can cost hours.
- **Every pull request links an issue assigned to its author**, maintainers included. Put `closes #N` in the PR body. Before writing code, get the issue assigned to the person the work is for (`/assign` when unassigned); if it is someone else's, don't start and tell the user. `/assign` works only on a `ready` issue, or on your own issue that is not `blocked`. If the bot refuses, don't start; tell the user the state: `needs-triage` waits for a maintainer, `needs-info` for its reporter, `blocked` for what its comments name. A maintainer claiming a `needs-triage` issue marks it `ready`. Exempt: trivial fixes (typos, links, comments), Renovate and Dependabot, and security fixes, which go through `SECURITY.md` and never reference the private report.
- **Work-in-progress limit: three open PRs and three assigned issues per contributor**, maintainers included. Drafts count; Renovate and Dependabot PRs don't, nor do issues typed Epic or Initiative (their sub-issues do). Check `gh pr list --author @me --state open` and `gh issue list --assignee @me --state open --search "-type:Epic -type:Initiative"` first. At three, stop and tell the user. Release an issue you no longer work on with `/unassign`.
- **Stay with the pull request after opening it.** Respond to comments and rebase when asked. Inactive pull requests are nudged at 7 days, marked stale at 14 and closed 7 days later.
- In the PR body, say what you ran and what you could not, and disclose AI assistance if a tool wrote a meaningful part of the change. The rest of the process is in `CONTRIBUTING.md`.

## Secrets and credentials

Hard boundaries. Violating one means a rotation, not a revert.

- **Never commit credentials, API keys, tokens, passwords, kubeconfigs or private keys**: not in source, test fixtures, `chart/values.yaml`, chainsaw manifests, `.github/workflows/` or a commit message. Examples use an obvious placeholder (`REPLACE_ME`, `<your-token>`), never a real value that "happens to be expired".
- **Never read a real credential into your output.** `~/.kube/config`, `~/.docker/config.json`, `~/.ssh/`, `~/.aws/` and any `.env` are off limits. Refer to them by path; never print them into the transcript, a file or a PR description.
- **Secret-bearing environment variables stay out of tracked files.** CI reads them through `${{ secrets.* }}`, local runs from your shell. No `.env` with real values, and no hardcoded fallback default for a secret-bearing variable.
- **Cluster secrets are mounted at runtime, never baked in.** Packages receive them as described in `docs/user-guide/providing-secrets.md`. Never inline a secret into a package `configMap`, a `NodeWright` CR or an image layer.
- **Found a committed secret? Stop and report it** through `SECURITY.md`, not a public issue. Don't quietly delete it in a follow-up commit: the value survives in git history and has to be rotated regardless.

## Commits and pushing

- **Conventional Commits.** Every commit is both signed off and cryptographically signed: `git commit -s -S`. `-s` adds the DCO `Signed-off-by` trailer; `-S` adds the GPG or SSH signature that `main`'s `required_signatures` ruleset and the Commit Requirements workflow check. Neither substitutes for the other, and amends need both (`git commit --amend -s -S --no-edit`). Signing needs an unsandboxed shell. No pseudonyms.
- **Review fixes are folded into the existing commit** and force-pushed, always with `git pushf`, the repository alias for `git push --force-with-lease --force-if-includes`. Never use a bare `git push --force`.
- A `stale info` rejection is that guard working, **not a cue to escalate to `--force`**. Fetch, find out what moved (a maintainer's merge of `main`, a co-author's commit, a bot's fixup) and integrate it.
- `--force-if-includes` tests reachability, not content: after rebasing onto `main` instead of merging the remote tip, `git pushf` keeps refusing. Merge the remote tip, or, once `git diff <remote-ref> HEAD` shows only your work, push with `git push --force-with-lease=<branch>:<sha-you-inspected>`.

## Docs, release notes and versions

- **Docs are part of every PR.** A change to user-visible behavior (CRD field, CLI command or flag, env var, annotation, metric, lifecycle semantics, install or upgrade flow) or to an architectural concept in `docs/` updates the affected page **in the same PR**. Fix a page your change makes wrong; delete a section it makes obsolete rather than leave two sources of truth. A behavior change without a `docs/` update is rejected in review.
- **`RELEASE_NOTES.md` is not a changelog, and most PRs don't belong in it.** Each component's `CHANGELOG.md` is generated from commit history. Write a note only when the reader has to **do** something or will be **surprised**: an upgrade-time action, a deprecation with a deadline, a behavior change they didn't ask for, a new knob worth discovering. A bug fix that restores intended behavior needs no entry. Default to none.
- **Components are versioned and tagged separately** (`operator/v0.15.0`, `cli/v0.3.0`, `agent/v6.4.0`, `chart/v0.15.0`), with strict semver per `docs/operations/versioning.md`.

## License headers

Every source file needs an Apache-2.0 header. Run `make fmt` (gofmt plus `make license-fmt`) before committing; never copy headers by hand. It only adds headers, so the year stays the year of first publication. It skips files whose content carries a `Code generated … DO NOT EDIT.` marker, a content check rather than a filename check, so a hand-written `zz_generated.*` still needs a header. `make license-header-check` is the CI gate and fails on any header that is not `SPDX-License-Identifier: Apache-2.0`. New Go files use `//` line comments, not `/* */`, because a block comment above a `//go:build` line is not legal.

## Issue and PR metadata

- **`.github/labels.yml` is the closed set of labels**, synced to GitHub with `make labels`. The sync creates and updates but never deletes, so treat any label not in the file as one that should not exist, never as precedent.
- **Never create a label**: no `gh label create`, no `gh issue create --label <new>`, nothing through `gh api`. If a label is genuinely missing, add it to `.github/labels.yml` in a PR and stop there.
- **Priority is not a label.** It is a native issue Field (Urgent / High / Medium / Low) that maintainers set during triage. Agents and reporters never set it and never apply `priority/*`, `P0`/`P1`/`P2` or severity labels. If something seems urgent, say so in the issue body.
- **Type is not a label either.** Bug / Enhancement / Documentation / Task / Epic / Initiative are native Issue Types set by the issue forms. `doc` is the one exception, applied by the PR path labeler to docs-only PRs.
- **When filing an issue, apply no labels.** `.github/workflows/triage.yaml` adds `needs-triage`, infers `component/*`, and keeps exactly one state label (`needs-triage`, `needs-info`, `blocked`, `ready`) on every open issue; `.github/labeler.yml` labels PRs by path. Never add or remove a state label unless a maintainer asks.
